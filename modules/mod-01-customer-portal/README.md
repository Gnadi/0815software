# MOD-01 · Customer Portal

Self-service access to orders, documents, and status. No account manager
required. Part of the [0815software](https://0815software.com) module
catalogue — standard business software, MIT-licensed, always free.

Customers sign in with email and password and see exactly their own data:
an order list with search and status filters, an order detail view with
line items and a status timeline (placed → confirmed → shipped →
delivered), and a document area with authenticated downloads of invoices,
delivery notes and statements. Strict tenant isolation is the core
correctness property — every query is scoped to the signed-in customer,
and requesting anyone else's order or document returns 404, proven by
tests.

## Stack

Deliberately standard and boring (same as MOD-02):

| Layer    | Choice                                        |
| -------- | --------------------------------------------- |
| Frontend | Vite + React 19 + TypeScript (strict)         |
| API      | Node + Express 5                              |
| Storage  | better-sqlite3 (single file, zero services)   |
| Styling  | Hand-rolled CSS, no framework                 |
| Tests    | Vitest + Supertest                            |

Runtime dependencies: `express`, `better-sqlite3`, `react`, `react-dom`.
Passwords are hashed with Node's built-in `crypto.scrypt` — no extra
auth dependency.

## Quickstart

Requires Node 20+.

```sh
cd modules/mod-01-customer-portal
npm install
npm run seed          # creates ./data.db + ./documents with demo data (idempotent)

# terminal 1 — API on :3001
npm run dev:api

# terminal 2 — UI on :5191 (proxies /api to :3001)
npm run dev:web
```

Open http://localhost:5191 and sign in with one of the demo accounts:

| Email                    | Password     | Customer             |
| ------------------------ | ------------ | -------------------- |
| `anna.berger@example.de` | `demo-anna`  | Berger Logistik GmbH |
| `l.steiner@example.at`   | `demo-lukas` | Steiner & Söhne      |
| `j.devries@example.nl`   | `demo-jan`   | De Vries Handel BV   |

Production-style single process (API + built client on one port):

```sh
npm run build
npm start             # http://localhost:3001
```

The server seeds an empty database automatically on first start, so
`npm run seed` is optional. No binary artifacts are committed — the demo
document files are plain text, generated by the seed script into
`./documents`. Delete `data.db` **and** `documents/` together to start
fresh.

## Data model

Five tables, created on demand (`server/db.ts`):

```
customers    id, email (unique), name, company, password_hash,
             token_version, created_at
orders       id, customer_id → customers, order_no (unique), status,
             currency, total_cents, placed_at
order_items  id, order_id → orders, sku, description, quantity,
             unit_price_cents
order_events id, order_id → orders, status, at, note      (the timeline)
documents    id, customer_id → customers, order_id → orders (nullable
             for standalone documents), doc_type, title, filename,
             stored_name (unique file name on disk), size_bytes,
             created_at
```

Money is stored as integer cents. An order's `status` is the status of
its latest event; the full history lives in `order_events`. Document
files live on disk under `DOCUMENTS_DIR`, named by `stored_name`; the
customer-facing `filename` is only used for the download.

## Auth model

- **Passwords** — `crypto.scrypt` with a random 16-byte salt, stored as
  `scrypt:<salt>:<key>`, compared with `timingSafeEqual`. Unknown emails
  burn the same scrypt work so login timing doesn't reveal whether an
  account exists.
- **Sessions** — stateless HMAC-SHA256-signed cookie (HttpOnly,
  SameSite=Lax, optional Secure), same pattern as MOD-02. The token
  carries the customer id, a per-customer token version and an expiry.
  Changing the password bumps the token version, which invalidates every
  previously issued token for that account; the change response carries
  a fresh token so the active session survives.

## Configuration

All via environment variables (see [`.env.example`](.env.example)):

| Variable            | Default                | Purpose                                  |
| ------------------- | ---------------------- | ---------------------------------------- |
| `PORT`              | `3001`                 | API / production server port             |
| `DATABASE_PATH`     | `./data.db`            | SQLite file (created on demand)          |
| `DOCUMENTS_DIR`     | `./documents`          | Document file storage (created on demand)|
| `SESSION_SECRET`    | `dev-secret-change-me` | HMAC key for the session cookie          |
| `SESSION_TTL_HOURS` | `12`                   | Session lifetime                         |
| `COOKIE_SECURE`     | `false`                | Set `true` behind HTTPS                  |

The server warns on startup while the default secret is in use. The dev
server does not load `.env` files by itself — export the variables in
your shell or use `node --env-file`.

## API

All routes under `/api`, JSON in/out. Session cookie required except for
`POST /api/login` and `GET /api/health`. Every data route is scoped to
the signed-in customer; ids belonging to other customers 404.

```
POST /api/login                   {email, password} → session cookie + customer profile
POST /api/logout
GET  /api/health
GET  /api/me                      profile of the signed-in customer
POST /api/me/password             {currentPassword, newPassword}
                                  401 wrong current, 422 too short (< 8 chars)
GET  /api/orders                  ?search= (order no. / SKU / description)
                                  &status= (placed|confirmed|shipped|delivered|cancelled)
GET  /api/orders/:id              {order, items, events, documents}
GET  /api/documents               all documents incl. standalone ones
GET  /api/documents/:id/download  file download (Content-Disposition: attachment)
```

## Scripts

| Script            | What it does                                            |
| ----------------- | ------------------------------------------------------- |
| `npm run dev:api` | API with reload (tsx watch)                             |
| `npm run dev:web` | Vite dev server with `/api` proxy                       |
| `npm run seed`    | Create/seed the SQLite database + demo document files   |
| `npm run build`   | Type-check (client + server) and build both to `dist/`  |
| `npm start`       | Run the production server (serves API + built client)   |
| `npm test`        | API tests (Vitest + Supertest, in-memory SQLite)        |

The tests cover login/logout, wrong credentials, token tampering, tenant
isolation on orders **and** documents, the status timeline, document
download content, and the password-change round-trip including session
invalidation.

## Deploy notes

- Any box with Node 20+ works: `npm ci && npm run build && npm start`
  under systemd, Docker, or a PaaS with a persistent disk — both the
  SQLite file and `DOCUMENTS_DIR` must survive restarts (mount volumes).
- Set `SESSION_SECRET` (`openssl rand -hex 32`) and `COOKIE_SECURE=true`,
  and terminate TLS in front (Caddy/nginx). This portal is
  customer-facing — never run it without HTTPS.
- Replace the seed data with your real customers/orders before going
  live (write to the same tables from your ERP export, or commission an
  import).
- Not a fit for serverless platforms: SQLite and the document store want
  a persistent filesystem.

## Out of scope (by design)

- **Order and document management** — this portal is read-only for
  business data. Creating orders, editing statuses and uploading
  documents is back-office work and belongs to
  [MOD-02 Admin Dashboard](../mod-02-admin-dashboard) or your ERP;
  data arrives here via the seed script or your own import.
- **Self-registration and password reset emails** — accounts are
  provisioned by the operator; there is no sign-up flow and no mail
  sending.
- **Profile editing** — customers can change their password, master
  data (name, company, email) is operator-managed.
- **Payments, carts, returns** — this is a portal, not a shop
  (see MOD-07 Storefront).
- **Roles, multiple users per company, SSO** — one login per customer
  account. If you need more, that's commissioned work — exactly the
  kind 0815software does.
