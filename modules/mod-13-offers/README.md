# MOD-13 · Offers

Write, send, and track sales offers (quotes / *Angebote*). A single-admin
tool for composing line-item offers with per-line discounts and VAT,
sending them to customers via a signed acceptance link, and tracking the
outcome — accepted, rejected, expired, withdrawn or superseded by a
revision.

Part of the [0815software](https://0815software.com) module catalogue.
Self-contained: one `package.json`, no external services, no SaaS, MIT.

---

## What it is

- **Customers** — CRUD master data (name, contact person, email, address,
  VAT id). A customer with offers is **archived, never hard-deleted**.
- **Offers** — a customer + a title + line items (description, quantity,
  unit net price in cents, VAT rate 0/10/20 %, optional per-line discount
  %) + a validity date + optional intro/terms text. Money totals are
  **always derived from the lines**, never stored.
- **Lifecycle** — `draft → sent → accepted / rejected`, plus `expired`
  (derived), `withdrawn` and `superseded`. Sent offers are **immutable**;
  changes are made by creating a **revision** (an append-only
  supersession chain).
- **Public acceptance link** — a sent offer gets an HMAC-signed customer
  token. The link `/offer/:ref?token=…` lets the customer view the offer
  and accept or reject it with no login. This is the "send to customer"
  mechanism (real email delivery is out of scope — the link is what you
  would email).
- **PDF export** — a letterhead-style offer PDF, generated by a hand-rolled
  zero-dependency writer.
- **UI** — dashboard, offer list (search / status filter / expired
  highlight), draft editor with a live totals preview, offer detail with a
  status timeline and the acceptance link, customer management, and a CSV
  export.

### Out of scope (deliberately)

- No email / SMS delivery — the app produces the acceptance link; sending
  it is your job.
- No multi-user accounts, roles or per-user audit — a single admin login
  guards the back office; the customer side is token-authenticated.
- No conversion to invoices, order management, payments or dunning (that
  is MOD-04 Invoice & Billing).
- No product catalogue / price book — line items are typed per offer.
- No multi-currency (EUR only) and no configurable VAT rates beyond
  0 / 10 / 20 %.
- No e-signature, no PDF/A, no digital certificates.
- No file uploads / attachments.

## Quickstart

```bash
npm install
npm run build      # type-check client + server, bundle the client
npm start          # serve API + built UI on http://localhost:3013
```

First start seeds an example dataset (5 customers, 12 offers across every
status and two years, including an expired offer, accepted offers and one
revision chain). Log in with the local-dev default **admin / admin**.

For development with hot reload, run the two processes side by side:

```bash
npm run dev:api    # API on :3013 (tsx watch)
npm run dev:web    # Vite dev server on :5203, proxying /api → :3013
```

Other scripts: `npm test` (Vitest + Supertest), `npm run seed` (seed a
database file from the CLI).

All settings come from the environment; every value has a local-dev
default. See [`.env.example`](./.env.example). The important ones:

| Variable          | Default                     | Purpose                                        |
| ----------------- | --------------------------- | ---------------------------------------------- |
| `PORT`            | `3013`                      | API / production server port                   |

| `ADMIN_PASSWORD`  | `admin`                     | **Change in production**                       |

| `SELLER_*`        | 0815software GmbH placeholders | Letterhead identity printed on the PDF      |

## Data model

SQLite (better-sqlite3, WAL, foreign keys on). Five tables:

- **`customers`** — `id, name, contact_person, email, vat_id, address,
  archived_at, created_at`.
- **`offers`** — `id, number, customer_id, title, status, valid_until,
  intro, terms, sent_at, supersedes_id, created_at`. `number` is unique.
  CHECK constraints make impossible states unrepresentable:
  - `(status = 'draft') = (number IS NULL)` — a numbered draft, or an
    un-numbered sent offer, cannot exist.
  - `(status = 'draft') = (sent_at IS NULL)`.
  - a non-draft always has a `valid_until`.
- **`offer_lines`** — `id, offer_id, position, description, quantity,
  unit_price_cents, vat_rate (0/10/20), discount_percent (0..100)`.
- **`offer_events`** — append-only status timeline: `id, offer_id, event
  (created/sent/accepted/rejected/withdrawn/superseded/revised), actor,
  note, created_at`.
- **`offer_counters`** — `year, last_seq` — the single source of offer
  numbers.

Two rules everything hangs off:

1. **No stored totals.** Offers store line items only. Net, VAT and gross
   are recomputed from the lines by one shared function
   (`shared/money.ts`) used by the API, the UI preview, the PDF, the CSV
   and the tests — so the numbers can never disagree.
2. **No stored "expired".** Expiry is derived at read time from
   `valid_until` versus an injectable clock, so it can never drift.

## Rules

### Money & rounding

All amounts are integer cents; euros exist only at the rendering edge.
Rounding follows Austrian/German practice:

- **line net** = `round(quantity × unit_price_cents × (1 − discount%/100))`
  — per-line rounding, *after* the line discount.
- **VAT** = `round(Σ line nets at a rate × rate / 100)` — computed once per
  rate on the discounted tax base, not per line.
- **gross** = net + VAT.

Example (a tested boundary): `3 × €0.33` at 20 % with a 10 % line discount
→ `round(99 × 0.9) = 89` net, `round(89 × 0.20) = 18` VAT, **€1.07** gross.

### Numbering

Offer numbers look like `OFF-2026-0001`: **gapless and sequential per
year**, assigned atomically at the moment a draft is *sent* — not at draft
creation. Drafts have no number. The `offer_counters` row for the year is
read-incremented-assigned inside one SQLite transaction, so concurrent
sends can never draw the same number and none is ever skipped. Deleting a
draft leaves no gap (it never had a number); an accepted / rejected /
withdrawn / superseded offer keeps its number forever.

### Validity & expiry

Every sent offer has a `valid_until` date. An offer whose validity date is
strictly before "today" reads as **expired** — a derived status, computed
against an injectable clock (the tests move the clock both directions; the
app uses the real UTC date). Accepting or rejecting an expired offer is a
`409`.

### Immutability & revisions

A sent offer is immutable: any edit to its lines, validity or text is a
`409`. To change it, create a **revision** — a fresh draft that copies the
content and points back at the original through `supersedes_id`. The
original moves to `superseded` (keeping its number) and points forward.
The chain is append-only: an already-superseded offer cannot be revised
again.

### Discounts

Each line may carry a discount percentage (0..100). The discount is
applied to that line's amount before per-line rounding; the offer's total
discount is shown as the difference between the gross-of-discount subtotal
and the net.

## Acceptance link (send to customer)

When an offer is sent it gains a stable token, `hmac("offer.<number>")`,
signed with `SESSION_SECRET`. The link you email the customer is:

```
<PUBLIC_BASE_URL>/offer/OFF-2026-0001?token=<hex>
```

- **View** — `GET /api/public/offers/:ref?token=…` returns a read-only
  view of the offer.
- **Accept / reject** — `POST …/accept` or `…/reject` records an
  append-only event (actor `customer`) and flips the status.
- A **missing, wrong or foreign** token returns `404` — exactly the same
  response as an unknown offer, so offer numbers leak nothing.
- Accepting an **expired** offer via the link returns `409` with a clear
  message.

The admin offer-detail view shows the composed link with a copy button.
Real email delivery is out of scope — the link is what you would send.

## API reference

Admin routes require the session cookie (`mod13_session`) from
`POST /api/login`. Public routes require only a valid offer token.

### Auth

| Method & path        | Purpose                              |
| -------------------- | ------------------------------------ |
| `POST /api/login`    | `{ username, password }` → session   |
| `POST /api/logout`   | Clear the session                    |
| `GET /api/me`        | Current admin username               |
| `GET /api/health`    | Liveness (public)                    |

### Customers

| Method & path                       | Purpose                                        |
| ----------------------------------- | ---------------------------------------------- |
| `GET /api/customers`                | List (`?search=`, `?archived=1`)               |
| `POST /api/customers`               | Create                                         |
| `GET /api/customers/:id`            | Read                                           |
| `PUT /api/customers/:id`            | Update                                         |
| `DELETE /api/customers/:id`         | Delete — `409` if the customer has offers      |
| `POST /api/customers/:id/archive`   | Archive (soft)                                 |
| `POST /api/customers/:id/unarchive` | Restore                                        |

### Offers

| Method & path                    | Purpose                                          |
| -------------------------------- | ------------------------------------------------ |
| `GET /api/offers`                | List (`?search=`, `?status=`)                    |
| `GET /api/offers/export.csv`     | CSV export of the current filter                 |
| `POST /api/offers`               | Create a draft                                   |
| `GET /api/offers/:id`            | Offer detail (lines, VAT breakdown, timeline, token) |
| `PUT /api/offers/:id`            | Update a draft — `409` once sent                 |
| `DELETE /api/offers/:id`         | Delete a draft — `409` once sent                 |
| `POST /api/offers/:id/send`      | Assign the number and send (`409` if not a draft)|
| `POST /api/offers/:id/withdraw`  | Withdraw a sent offer (keeps its number)         |
| `POST /api/offers/:id/accept`    | Record acceptance (staff-side)                   |
| `POST /api/offers/:id/reject`    | Record rejection (staff-side)                    |
| `POST /api/offers/:id/revise`    | Create a revision (supersedes the original)      |
| `GET /api/offers/:id/pdf`        | Offer PDF                                         |
| `GET /api/stats`                 | Derived dashboard figures (`?period=YYYY`)       |

### Public (offer token)

| Method & path                          | Purpose                          |
| -------------------------------------- | -------------------------------- |
| `GET /api/public/offers/:ref`          | Read-only view (`?token=`)       |
| `POST /api/public/offers/:ref/accept`  | Customer accepts (`?token=`)     |
| `POST /api/public/offers/:ref/reject`  | Customer rejects (`?token=`)     |

Errors are JSON `{ error, details? }` with status `401` (unauth), `404`
(not found / bad token), `409` (illegal transition) or `422` (validation,
with a `details` array of `{ field, message }`).

## Stack

- **Client** — Vite + React 19 + TypeScript (strict). Hand-rolled CSS in
  the 0815 token idiom; no component or router libraries.
- **Server** — Express 5 + better-sqlite3. Stateless HMAC session cookie
  (single admin from env vars) and HMAC offer tokens.
- **PDF** — a ~250-line hand-rolled PDF 1.4 writer (base-14 fonts, WinAnsi,
  uncompressed streams). No PDF dependency.
- **Tests** — Vitest + Supertest against an in-memory database, driving the
  clock explicitly.

## Deploy notes

`npm run build` emits the client to `dist/client` and the compiled server
to `dist/server`; `npm start` serves both from `PORT`. Run it behind a TLS
terminator and set `COOKIE_SECURE=true`. Point `DATABASE_PATH` at a
persistent volume and set a strong `SESSION_SECRET`, `ADMIN_PASSWORD` and
`PUBLIC_BASE_URL`. Everything is process-local — a single instance backed
by one SQLite file. No external dependencies to provision.
