# MOD-09 · Document Management

Upload, tag, version, and control access to documents. Access is
**matter-based**: every document belongs to exactly one matter (or
project), and you see a matter only if you have been granted membership on
it. Part of the [0815software](https://0815software.com) module catalogue
— standard business software, MIT-licensed, always free.

Users sign in with a username and password. Each user has a global role
(`admin` or `member`) and, per matter, an access level (`viewer`,
`editor`, `owner`). Documents carry an append-only version history: every
upload adds a new, immutable version with its own SHA-256, size, uploader
and timestamp; the "current" version is always derived as the latest one.
The core correctness property is **matter isolation** — a user with no
membership on a matter learns nothing about it, not even that it exists
(requests return `404`, never `403`), proven by tests on every read,
download, version and tag endpoint.

## Stack

Deliberately standard and boring (same as the other modules):

| Layer    | Choice                                        |
| -------- | --------------------------------------------- |
| Frontend | Vite + React 19 + TypeScript (strict)         |
| API      | Node + Express 5                              |
| Storage  | better-sqlite3 + content-addressed files on disk |
| Styling  | Hand-rolled CSS, no framework                 |
| Tests    | Vitest + Supertest                            |

Runtime dependencies: `express`, `better-sqlite3`, `react`, `react-dom`.
Passwords are hashed with Node's built-in `crypto.scrypt`; uploads are
parsed with Express's built-in `raw` body parser — no `multer`, no extra
auth or upload dependency.

## Quickstart

Requires Node 20+.

```sh
cd modules/mod-09-document-management
npm install
npm run seed          # creates ./data.db + ./storage with demo data (idempotent)

# terminal 1 — API on :3009
npm run dev:api

# terminal 2 — UI on :5199 (proxies /api to :3009)
npm run dev:web
```

Open http://localhost:5199 and sign in with one of the demo accounts:

| Username | Password     | Global | Matter access                                            |
| -------- | ------------ | ------ | -------------------------------------------------------- |
| `admin`  | `demo-admin` | admin  | implicit **owner** on every matter                       |
| `mara`   | `demo-mara`  | member | owner `MAT-2026-014`, viewer `MAT-2026-033`              |
| `theo`   | `demo-theo`  | member | editor `MAT-2026-014`, owner `MAT-2026-021`, viewer `033`|
| `iris`   | `demo-iris`  | member | viewer `MAT-2026-021`, owner `MAT-2026-033`              |

The overlapping-but-distinct memberships make isolation easy to see: log
in as `mara` and `MAT-2026-021` simply does not exist for her.

Production-style single process (API + built client on one port):

```sh
npm run build
npm start             # http://localhost:3009
```

The server seeds an empty database automatically on first start, so
`npm run seed` is optional. **No binary artifacts are committed** — the
demo files are plain text generated by the seed script into `./storage`.
Delete `data.db` **and** `storage/` together to start fresh.

## Data model

Six tables, created on demand (`server/db.ts`):

```
users             id, username (unique), name, role (admin|member),
                  password_hash, token_version, created_at
matters           id, key (unique), name, description, created_by → users,
                  created_at
matter_members    id, matter_id → matters, user_id → users,
                  role (viewer|editor|owner), created_at,
                  UNIQUE(matter_id, user_id)          -- the access boundary
documents         id, matter_id → matters, title, created_by → users,
                  created_at, deleted_at (nullable)   -- soft delete
document_versions id, document_id → documents, version_no, size_bytes,
                  sha256, content_type, filename, storage_path,
                  uploaded_by → users, uploaded_at,
                  UNIQUE(document_id, version_no)      -- append-only chain
document_tags     id, document_id → documents, tag, UNIQUE(document_id, tag)
```

Uploaded bytes are stored on disk under `STORAGE_DIR`, **content-addressed
by their SHA-256 hash** (`storage_path` is the hash). Identical bytes
across versions or documents are therefore stored once and never mutated.
The database holds only metadata plus the path.

## Access-control model

Access is decided in exactly one place — `requireMatterAccess(db, user,
matterId, minRole)` in `server/docs.ts` — and every matter-scoped route
goes through it (directly, or via `requireDocumentAccess`, which resolves a
document to its owning matter first). No route makes an ad-hoc access
decision.

Per-matter roles are ranked `viewer (1) < editor (2) < owner (3)`:

| Role       | Can do                                                     |
| ---------- | ---------------------------------------------------------- |
| **viewer** | read metadata, list versions, download any version        |
| **editor** | + upload new documents and versions, add/remove tags       |
| **owner**  | + manage matter members, soft-delete documents             |
| **admin**  | implicit **owner** on every matter, plus user/matter admin |

The security contract enforced by the helper:

- **No membership ⇒ 404, never 403.** A non-member (and non-admin) asking
  for a matter or document — even by a valid, guessed id — gets the exact
  same `404 Not found` as for a non-existent id. Existence is never
  leaked. A matter-filtered document list for an inaccessible matter comes
  back empty, not as an error.
- **Insufficient role ⇒ 403.** A member who *can* see the matter but lacks
  the required level gets a clear `403` (e.g. a viewer trying to upload, an
  editor trying to manage members). They already know the matter exists,
  so there is nothing to hide.
- **Admins** implicitly hold `owner` on every matter that exists.

## Versioning rules

- A document's version chain is **append-only**. Uploading a new version
  never mutates or deletes prior versions.
- `version_no` is derived per document as `MAX(version_no) + 1`, so
  numbering is **gapless** and monotonic (1, 2, 3, …).
- The **current version is derived** — always `MAX(version_no)` — never a
  stored mutable pointer that could drift.
- Downloads default to the current version; any specific version is
  downloadable by number (subject to access), via
  `/api/documents/:id/versions/:n/download`.
- Deleting a document is a **soft delete** (owner/admin only): it sets
  `deleted_at`, which hides the document from all lists and reads (404),
  while the version rows and their bytes are retained. **Hard delete —
  destroying versions or blobs — is intentionally out of scope.**

## Uploads

Upload endpoints take the file **bytes as the raw request body**; metadata
rides on the query string (`title`, `filename`) and the `Content-Type`
header supplies the stored content type. The server hashes the bytes,
stores the blob, and records `size_bytes` + `sha256`. Uploads over
`MAX_UPLOAD_BYTES` (default 25 MiB) are rejected with `413`; an empty body
is `422`.

## Auth model

- **Passwords** — `crypto.scrypt` with a random 16-byte salt, stored as
  `scrypt:<salt>:<key>`, compared with `timingSafeEqual`. Unknown
  usernames burn the same scrypt work so login timing doesn't reveal
  whether an account exists.
- **Sessions** — stateless HMAC-SHA256-signed cookie (`mod09_session`,
  HttpOnly, SameSite=Lax, optional Secure). The token carries the user id,
  a per-user token version and an expiry. Changing the password bumps the
  token version, invalidating every previously issued token; the change
  response carries a fresh token so the active session survives.

## Configuration

All via environment variables (see [`.env.example`](.env.example)):

| Variable            | Default                | Purpose                                   |
| ------------------- | ---------------------- | ----------------------------------------- |
| `PORT`              | `3009`                 | API / production server port              |
| `DATABASE_PATH`     | `./data.db`            | SQLite file (created on demand)           |
| `STORAGE_DIR`       | `./storage`            | Content-addressed blob store (on demand)  |
| `MAX_UPLOAD_BYTES`  | `26214400` (25 MiB)    | Reject larger uploads with 413            |
| `SESSION_SECRET`    | `dev-secret-change-me` | HMAC key for the session cookie           |
| `SESSION_TTL_HOURS` | `12`                   | Session lifetime                          |
| `COOKIE_SECURE`     | `false`                | Set `true` behind HTTPS                   |

The server warns on startup while the default secret is in use. The dev
server does not load `.env` files by itself — export the variables in your
shell or use `node --env-file`.

## API

All routes under `/api`, JSON in/out (except uploads and downloads).
Session cookie required except for `POST /api/login` and `GET /api/health`.
Matter-scoped routes 404 for matters/documents the user cannot see and 403
when the role is insufficient.

```
POST   /api/login                     {username, password} → session cookie + profile
POST   /api/logout
GET    /api/health
GET    /api/me                        signed-in user profile
POST   /api/me/password               {currentPassword, newPassword}

GET    /api/users                     shared directory (id, username, name, role)
POST   /api/users                     admin only — create a user

GET    /api/matters                   matters the user can see (admin: all)
POST   /api/matters                   admin only — create a matter
GET    /api/matters/:id               matter summary (viewer+)
GET    /api/matters/:id/members       list members (viewer+)
POST   /api/matters/:id/members       owner+ — {user_id, role} add/update a member
DELETE /api/matters/:id/members/:uid  owner+ — remove a member

GET    /api/documents                 ?matter= &tag= &search=  (title search)
GET    /api/tags                      distinct tags across visible documents
GET    /api/documents/:id             {document, versions, activity, matter_role}
POST   /api/matters/:id/documents     editor+ — raw body upload → new doc (v1)
                                      ?title= &filename= , Content-Type = file type
POST   /api/documents/:id/versions    editor+ — raw body upload → next version
GET    /api/documents/:id/download    current version (viewer+); ?version=N for a specific one
GET    /api/documents/:id/versions/:n/download   a specific version (viewer+)
POST   /api/documents/:id/tags        editor+ — {tag}
DELETE /api/documents/:id/tags/:tag   editor+ — remove a tag
DELETE /api/documents/:id             owner+ — soft delete
```

Downloads set `Content-Disposition: attachment`, plus `X-Version-No` and
`X-Content-SHA256` response headers.

## Scripts

| Script            | What it does                                            |
| ----------------- | ------------------------------------------------------- |
| `npm run dev:api` | API with reload (tsx watch)                             |
| `npm run dev:web` | Vite dev server with `/api` proxy                       |
| `npm run seed`    | Create/seed the SQLite database + demo files            |
| `npm run build`   | Type-check (client + server) and build both to `dist/`  |
| `npm start`       | Run the production server (serves API + built client)   |
| `npm test`        | API tests (Vitest + Supertest, in-memory SQLite)        |

The tests cover login/logout, wrong credentials, token tampering,
cross-matter isolation returning **404** on read/download/version/tag for a
non-member, role escalation blocked (`viewer`→upload 403, `editor`→member
management 403, `editor`→soft-delete 403), append-only gapless version
numbering, derived current version, SHA-256 recorded and matching the
served bytes, soft-delete hides-but-retains, the 25 MiB size limit (413)
and empty upload (422), admin implicit access, unauth 401, and the
password-change round-trip including session invalidation.

## Deploy notes

- Any box with Node 20+ works: `npm ci && npm run build && npm start`
  under systemd, Docker, or a PaaS with a persistent disk — both the
  SQLite file and `STORAGE_DIR` must survive restarts (mount volumes).
- Set `SESSION_SECRET` (`openssl rand -hex 32`) and `COOKIE_SECURE=true`,
  and terminate TLS in front (Caddy/nginx). Never run without HTTPS.
- Replace the seed data with your real users/matters before going live.
- Not a fit for serverless platforms: SQLite and the blob store want a
  persistent filesystem. For large-scale storage, swap `server/storage.ts`
  for an object-store backend (S3-compatible) — the metadata model is
  unchanged.

## Out of scope (by design)

- **Hard delete / purge** — deletes are soft; version bytes are retained
  for audit. Physically destroying blobs (retention policies, legal holds,
  GDPR erasure) is deliberately not built in.
- **Full-text search inside documents** — search is over titles and tags,
  not file contents. No OCR, no content indexing.
- **In-browser preview / thumbnails / editing** — documents are stored and
  downloaded as opaque bytes; there is no viewer or online editor.
- **Concurrent-edit locking, check-in/check-out** — versioning is
  append-only, not a locking workflow.
- **Self-registration, password-reset emails, SSO/SAML** — accounts are
  provisioned by an admin; there is no sign-up flow and no mail sending.
- **Per-document ACLs, sharing links, external guests** — access is granted
  at the matter level only. If you need finer or public sharing, that's
  commissioned work — exactly the kind 0815software does.
